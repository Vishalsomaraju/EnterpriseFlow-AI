# Workflow Engine & Schemas

## Overview
The Workflow Engine is the deterministic heart of EnterpriseFlow AI. It is responsible for parsing rules, validating graphs, and performing exact mathematical and logical traversals for Impact Analysis.

## Canonical Objects

The system strictly adheres to the following canonical objects and their lifecycle:

`WorkflowExtraction` → `WorkflowGraph` → `AutomationBlueprint` → `ImplementationPlan` → `Implementation` → `ChangeImpact`

### 1. WorkflowExtraction
The raw structured output from the AI Document Parser. It contains nodes, edges, rules, and ambiguities. This object must be validated against a JSON schema before proceeding.

### 2. WorkflowGraph
**This is the canonical source of truth for workflow structure.** It represents the validated, mathematically sound directed graph of the business process.

### 3. WorkflowNode & WorkflowEdge
The building blocks of the `WorkflowGraph`.
- **Node**: A discrete step (e.g., "Manager Approval").
- **Edge**: The transition between nodes, often guarded by a `BusinessRule`.

### 4. BusinessRule
The logic dictating behavior (e.g., `invoice.amount > 500000`). These are evaluated by the deterministic rule engine, not an LLM.

### 5. AutomationBlueprint
The translation of the `WorkflowGraph` into software requirements (services, APIs, data entities).

### 6. ImplementationPlan
The step-by-step coding plan generated by Bob based on the `AutomationBlueprint`.

### 7. Dependency
The concrete links connecting `BusinessRule` → `CodeFile`, `TestFile`, and `Documentation`.

### 8. ChangeImpact
The resulting report when a `BusinessRule` is modified.

## The Impact Analysis Mandate

> [!CAUTION]
> **Impact analysis must traverse stored dependencies and relationships rather than asking an LLM to guess affected components.**

When a rule changes (e.g., threshold from ₹500,000 to ₹1,000,000), the Impact Engine must execute a deterministic graph traversal:

1. Identify the modified `BusinessRule`.
2. Query the `Dependency` table to find all `CodeFiles` directly implementing this rule.
3. Query the `Dependency` table to find all `TestFiles` validating this rule.
4. Query the `WorkflowGraph` to find downstream `WorkflowNodes` affected by the change.
5. Generate the `ChangeImpact` report containing exactly those items—no false positives, no missed dependencies.
